# Recovery foundation checkpoint

**Date:** 27 September 2026  
**Scope:** Portions of M0–M3 and M5; not a release candidate.

## Implemented

- `Relight.Core` contains policy validation, lifecycle states, observation provenance, transition results and a per-profile recovery model driven by caller-supplied monotonic elapsed time and discovery outcomes.
- The model handles first-start adoption, absence confirmation, retry deadlines, exact reservation caps, appearance timeout, early exit, intervention lockout, external-start observation and rearming, pause/unavailable gaps, policy edits, explicit starts and stale launch operations.
- The model exports a checkpoint without process identity or monotonic deadlines. Restore conservatively requires fresh discovery, preserves reserved attempts and lockout, and marks an interrupted final reservation locked out pending stable observation or explicit reset.
- `Relight.Storage` writes versioned, checksummed, revision-checked per-profile state snapshots. It flushes a temporary file before atomic replacement and keeps a prior backup. Corrupt, missing, unsupported or stale state fails closed; it does not silently load a backup and refund an attempt.
- `Relight.Storage` also has separate versioned configuration with explicit first-run initialization, validated profile/global settings, atomic replacement, a last-good backup, revision plus content-hash concurrency checks, and conservative enabled-profile overlap validation. If the current file is damaged or externally edited into an invalid form, the backup can be displayed with automatic actions suspended. Multi-session coordination is pending.
- An explicit storage repair operation can restore only the same last-good backup that was displayed. It rejects a changed backup or an already repaired current file, preserves the invalid current bytes in a separate `configuration-invalid-*.json` file, and atomically restores the backup without overwriting that backup. The Settings action confirms the backup revision/profile count, repairs it, then restarts the host so recovery state is loaded conservatively before any automatic dispatch. When both files are invalid, no trusted backup exists for this action and a fuller repair/import path is still needed.
- `Relight.Storage` has an asynchronous JSON Lines event journal under a `Logs` subdirectory. Its typed schema carries UTC event, profile, episode and operation IDs without argument, environment or window-content fields. Writes rotate at the configured size; retention checks age and total size and deletes only regular files with the journal's exact generated-name pattern. I/O failure sets degraded status and buffers a bounded number of events for replay. A bounded, non-blocking recorder queue now carries coordinator transitions and launch outcomes to the journal. A filtered History page and event-count summary are available; the complete event taxonomy and diagnostics remain pending. See [the History checkpoint](history-checkpoint.md).
- `Relight.TestTarget` is a controllable Windows Forms process that can exit on a timer, spawn a helper, hand off from a short-lived launcher, accept or refuse graceful close, and report its PID/start time to a disposable ready file.
- `Relight.Engine` provides a per-profile coordinator with serialized ticks and pause commands. It discovers twice before an automatic dispatch, durably reserves the attempt, prevents a launch if the write fails, and lets independent profiles progress while another launch blocks. A pause request cancels a cooperative blocked launch without refunding its reservation.
- `Relight.Engine` now also has one shared monotonic scheduler. It scans profile deadlines once per second, starts due ticks independently, advances absence/retry/appearance/observation deadlines before the slower normal interval, rejects a second in-flight tick for the same profile, and cancels ticks when a profile is removed. A shared bounded launch gate can limit simultaneous dispatches across profiles. Coordinators acquire a slot before the final lookup and reservation, so a target appearing while queued is adopted without a charge. A queued pause cancels without a reservation; a pause after reservation keeps its charge. Name and monitoring/recovery policy edits now reconcile the scheduler without replacing the profile coordinator.
- `Relight.Windows` provides an executable launch/discovery adapter. Launch uses `ProcessStartInfo.ArgumentList`; discovery requires an exact canonical executable path, the current Windows user SID and session, and records PID plus start time. Optional exact argument selectors distinguish a main process from a same-path helper. Ambiguous or inaccessible candidates produce unavailable detection. This adapter does not activate installed apps or establish a logical handoff contract.
- `Relight.Windows` now composes configuration, existing runtime state, executable adapters, the shared scheduler/gate and queued journal in `RecoveryApplicationHost`. A genuinely empty data directory gets empty configuration. An existing enabled profile with missing/damaged state is never given a new budget; its executable remains under read-only passive discovery on the shared scheduler. Invalid current configuration can show last-good profiles with automatic actions suspended. Unsupported packaged profiles remain inactive. The WPF app starts the host for normal launches and displays its profile snapshots. The shell smoke script uses `--shell-test` to bypass monitoring during forced process interruption.
- Basic executable registration now inspects current-session identity before enablement, writes the initial durable state before publishing enabled configuration, rejects overlapping targets and joins the live scheduler. The WPF Add dialog browses for an executable, displays the discovery result and explains the wait-for-first-start default. Arguments, working directory and installed-app selection remain pending. A failed configuration commit may leave an unreferenced ledger; it cannot become an enabled profile or be silently reused.
- The coordinator exposes durable pause/resume, enable/disable and Reset recovery commands. Pause/resume and enable/disable preserve the attempt count and lockout; reset rejects an in-flight launch, checks target presence, clears the episode budget durably and begins a fresh observation or absence/retry sequence. A failed state write degrades storage and prevents dispatch. The host runs per-profile commands independently off the WPF dispatcher, and dashboard rows expose these controls when applicable. Stop/restart, launch-identity editing and complete UI acceptance remain pending.
- Start now now flows through the same coordinator and shared launch gate. It checks current-session identity immediately before dispatch, adopts a present instance, durably records an explicit pending operation before launching an absent target and does not charge or clear the automatic budget. A failed pending-operation write prevents dispatch. If launch reporting is uncertain, the coordinator waits through the appearance timeout instead of allowing an immediate duplicate. An interrupted explicit operation restores into a distinct hold, even when the automatic budget is zero; discovery and qualifying stable observation can rearm it under policy, or the user can explicitly reset recovery. The state file adds optional fields so existing schema-1 checksums remain valid. This conservative interrupted-explicit hold is a provisional M2 safety choice pending fuller restart/session validation. The dashboard exposes Start now for applicable executable profiles. A dispatch that reports failure after the adapter was entered is currently treated as uncertain for the full appearance timeout, even if the error may have been definite. Restart now and Stop and pause remain pending.
- Disable and remove now cancel pending dispatch before committing configuration and detaching the scheduler; neither terminates the target. Re-enable opens the existing state file and fails closed if it is missing or damaged. Removed profiles leave their state file and events intact, while the dashboard no longer lists them. A stale configuration save rolls back the enablement ledger when possible. A disposable Windows target remained running through disable, re-enable and remove in the controlled integration test. Per-profile View history selects its current profile ID; removed profiles with retained events remain selectable in History.
- The WPF Edit policy dialog now changes the immutable profile's display name and its monitoring/recovery policy while showing target identity read-only. The host commits validated, revision-checked configuration under the profile coordinator's serialization gate, so a stale save leaves the live policy unchanged. Observation-duration changes restart the current stability timer; retry-delay changes recompute the pending deadline from Save; the scheduler immediately reconciles with new intervals. An outstanding launch retains its original appearance deadline, attempt limit and retry delay until its result. Renaming keeps the same profile ID, ledger and history. Launch identity, notification preferences and richer setup remain open.
- The test suite covers deterministic recovery boundaries, restart reconstruction, damaged state and real Windows process behaviors. The Windows build workflow runs deterministic tests; process/window tests run in an interactive local session.

## Verification and limits

`dotnet test Relight.slnx -c Release --no-restore` passed **88 tests** on this Windows 11 x64 desktop, including name/policy edits with an active controlled target, live observation/retry timing, in-flight policy snapshots, stale-save rollback, removed-profile cataloging in History, explicit configuration repair safeguards and host reopening after repair. The host repair test was strengthened afterward to verify an existing profile and state ledger survive; its focused rerun passed. `dotnet build Relight.slnx -c Release` passed with zero warnings/errors. `pwsh -File scripts/Test-Shell.ps1` passed for the Settings repair change. [Windows CI for the Settings repair action](https://github.com/nkimber/Relight/actions/runs/36349922581) passed its Release build and deterministic subset before the stronger test assertion.

The controlled integration test can launch the disposable test target and leaves it running after host disposal or profile removal. Registration is tested with the disposable executable. The Add dialog opened in a live WPF preview and focused the name field; its explanatory text was clipped at 430 pixels, so its height was increased to 510 pixels. That layout repair, the profile action buttons, editor and Settings repair action were not visually rechecked because another application became foreground during the second inspection. No real user target was configured or exercised in the WPF process. Repair when both configuration copies are invalid and launch-identity editing are not available. Notifications, packaged-app activation, session-scoped live state, cross-sign-in lockout coordination and some user controls remain open. M1–M6 exit criteria are therefore not claimed complete.

The Windows adapter depends on Microsoft's `System.Management` 10.0.11 package for process command lines and owner SID checks. Its [NuGet package page](https://www.nuget.org/packages/System.Management/10.0.11) identifies the Microsoft MIT license; carry its notice into release dependency review. WMI inspection and exact executable paths can become unavailable after an application update. Neither packaged target has been controlled by this adapter.

State writes are designed to survive application interruption. A separate power-loss and cross-session validation gate remains: flushing the temporary file and replacing it atomically are not proof against every storage device or OS failure mode.
