# Recovery foundation checkpoint

**Date:** 27 September 2026  
**Scope:** Portions of M0–M3 and M5; not a release candidate.

## Implemented

- `Relight.Core` contains policy validation, lifecycle states, observation provenance, transition results and a per-profile recovery model driven by caller-supplied monotonic elapsed time and discovery outcomes.
- The model handles first-start adoption, absence confirmation, retry deadlines, exact reservation caps, appearance timeout, early exit, intervention lockout, external-start observation and rearming, pause/unavailable gaps, policy edits, explicit starts and stale launch operations.
- An unavailable detection discards a pending retry deadline. A retry tick more than five seconds late conservatively restarts absence confirmation and the retry delay, preventing an immediate launch after a long monitoring gap. This is deterministic model coverage; actual Windows sleep/unlock notification and reconciliation timing remain unverified.
- The model exports a checkpoint without process identity or monotonic deadlines. Restore conservatively requires fresh discovery, preserves reserved attempts and lockout, and marks an interrupted final reservation locked out pending stable observation or explicit reset.
- `Relight.Storage` writes versioned, checksummed, revision-checked per-profile state snapshots. It flushes a temporary file before atomic replacement and keeps a prior backup. Corrupt, missing, unsupported or stale state fails closed; it does not silently load a backup and refund an attempt.
- Shared-budget and session-state repositories exist for the cross-sign-in design. The session repository keeps live checkpoints under an opaque logon key and rejects missing or changed shared-budget revisions; a new sign-in does not adopt another sign-in's pending launch as its own. Ordinary host startup now composes them; real two-sign-in behavior remains unverified. See [session coordination](session-coordination.md).
- A migration transaction validates and locks legacy state, archives the original bytes, writes a legacy-path tombstone and pending ownership marker before creating new budget/session records, and switches to a completed owner marker afterward. Upgraded legacy readers/writers reject either marker; known older readers/writers fail on the tombstone. Ordinary host startup now invokes guarded migration for valid legacy profiles. Cross-process rollout validation and general partial-migration repair remain open.
- An opt-in coordinator path now commits episode start, automatic and explicit launch markers, marker resolution, lockout and stable/manual budget release to the shared ledger before session-state writes. A final discovery after either launch marker averts dispatch when the target appeared or inspection became unavailable; automatic reservations stay charged. On a same-session restart, a matching pending marker is reconciled only after target presence or a fresh full appearance timeout of repeatedly verified absence. The scheduler polls at the observation interval during that wait. Unknown detection, a missed poll, pause or disable restarts it; pause/disable preserve ownership across another restart. A foreign or unmatched marker suspends automatic actions. Ordinary host startup now passes these stores.
- `Relight.Storage` also has separate versioned configuration with explicit first-run initialization, validated profile/global settings, atomic replacement, a last-good backup, revision plus content-hash concurrency checks, and conservative enabled-profile overlap validation. If the current file is damaged or externally edited into an invalid form, the backup can be displayed with automatic actions suspended. Multi-session coordination is pending.
- An explicit storage repair operation can restore only the same last-good backup that was displayed. It rejects a changed backup or an already repaired current file, preserves the invalid current bytes in a separate `configuration-invalid-*.json` file, and atomically restores the backup without overwriting that backup. The Settings action confirms the backup revision/profile count, repairs it, then restarts the host so recovery state is loaded conservatively before any automatic dispatch. When both files are invalid, no trusted backup exists for this action and a fuller repair/import path is still needed.
- Current-user sign-in startup uses a quoted `Relight.exe --tray` command in the user's Windows Run key. Settings and tray actions call one host command that applies registration and saves the global preference with a revision check; a failed save rolls registration back. The UI reports the actual entry and discrepancies. In-memory adapter tests cover command quoting, older-path replacement, conflicting values and rollback; a host test covers a stale configuration save. Actual sign-in, relocation and startup-disabled-by-Windows behavior are not yet verified.
- Tray Pause all and Resume all fan out to the same per-profile durable pause command. Eligible profiles progress independently, and partial failures report completed/requested counts with per-profile errors. A controlled integration test damages one ledger and verifies another profile still pauses and resumes; no target is stopped by these commands. The tray interactions have not received interactive visual verification.
- The tray summary is derived from current hosted profile snapshots and global configuration/logging problems, with attention taking priority over recovery, healthy monitoring and all-paused/disabled status. The tooltip uses bounded plain-language counts; separate flame variants add exclamation, recovery and pause cues. Unit tests cover priority and the Windows tooltip limit. Generated icon artwork was inspected in a side-by-side preview; live state changes in the notification area are not yet visually verified.
- Live Lockout entered and stable automatic Observation completed events also pass through a bounded in-memory notification tap. The WPF status tick drains it, applies per-profile preferences and one-notice-per-episode memory, and asks `NotifyIcon` for a best-effort balloon. A display exception is shown in the dashboard banner and does not reach recovery coordination. The tap can discard old candidates if more than 256 relevant events arrive before the UI drains it; real Windows delivery, suppression behavior and accessibility have not been checked interactively.
- Dashboard rows now render retry eligibility, appearance timeout and uninterrupted stability qualification against the host's monotonic elapsed time, alongside attempt budget, last in-session verification and logical current-session instance status. Overdue observation is labeled unverified. Existing row objects are updated in place to preserve keyboard focus as one-second countdown text changes. A 30-second asynchronous scan of retained event history shows each profile's last recorded disappearance and last stable automatic recovery; missing or malformed history is labeled as incomplete. Focused tests cover timer boundaries, overdue observation, row identity and latest event selection; interactive UI acceptance remains open.
- The Applications view now filters all/attention/recovering/protected/paused-or-disabled and sorts by name/status priority/attempts. It keeps the unfiltered profile list for History and reports an empty filter result explicitly. View-model tests cover filtering, sorting and retained row identity; actual keyboard and screen-reader behavior remains to be checked interactively.
- `Relight.Storage` has an asynchronous JSON Lines event journal under a `Logs` subdirectory. Its typed schema carries UTC event, profile, episode and operation IDs without argument, environment or window-content fields. Writes rotate at the configured size; retention checks age and total size and deletes only regular files with the journal's exact generated-name pattern. I/O failure sets degraded status and buffers a bounded number of events for replay. A bounded, non-blocking recorder queue now carries coordinator transitions and launch outcomes to the journal. A filtered History page and event-count summary are available; the complete event taxonomy and diagnostics remain pending. See [the History checkpoint](history-checkpoint.md).
- `Relight.TestTarget` is a controllable Windows Forms process that can exit on a timer, spawn a helper, hand off from a short-lived launcher, accept or refuse graceful close, and report its PID/start time to a disposable ready file.
- `Relight.Engine` provides a per-profile coordinator with serialized ticks and pause commands. It discovers twice before an automatic dispatch, durably reserves the attempt, prevents a launch if the write fails, and lets independent profiles progress while another launch blocks. A pause request cancels a cooperative blocked launch without refunding its reservation.
- `Relight.Engine` now also has one shared monotonic scheduler. It scans profile deadlines once per second, starts due ticks independently, advances absence/retry/appearance/observation deadlines before the slower normal interval, rejects a second in-flight tick for the same profile, and cancels ticks when a profile is removed. A shared bounded launch gate can limit simultaneous dispatches across profiles. Coordinators acquire a slot before the final lookup and reservation, so a target appearing while queued is adopted without a charge. A queued pause cancels without a reservation; a pause after reservation keeps its charge. Name and monitoring/recovery policy edits now reconcile the scheduler without replacing the profile coordinator.
- `Relight.Windows` provides an executable launch/discovery adapter. Launch uses `ProcessStartInfo.ArgumentList`; discovery requires an exact canonical executable path, the current Windows user SID and session, and records PID plus start time. Optional exact argument selectors distinguish a main process from a same-path helper. Ambiguous or inaccessible candidates produce unavailable detection. This adapter does not activate installed apps or establish a logical handoff contract.
- A separate read-only packaged-process probe uses the Windows package-family API, current-session and owner-SID checks, and PID/start time to list candidates without versioned installation paths. For the user-selected ChatGPT package, a target-specific discovery adapter distinguishes an observed Electron main process from `--type=` helpers, conservatively returning unavailable if a candidate cannot be verified or if multiple main candidates remain. An AUMID launcher uses Windows application activation without trusting its returned PID. Both adapters were exercised against the already-running ChatGPT package and are wired into the host for this selected package. No packaged-app stop adapter exists, so Stop and pause and Restart now remain unavailable for it.
- `Relight.Windows` now composes configuration, existing runtime state, executable and selected-ChatGPT adapters, the shared scheduler/gate and queued journal in `RecoveryApplicationHost`. A genuinely empty data directory gets empty configuration. An existing enabled profile with missing/damaged state is never given a new budget; supported targets remain under read-only passive discovery on the shared scheduler. Invalid current configuration can show last-good profiles with automatic actions suspended. Other packaged profiles remain inactive. The WPF app starts the host for normal launches and displays its profile snapshots. The shell smoke script uses `--shell-test` to bypass monitoring during forced process interruption.
- Basic executable and selected-ChatGPT registration now inspect current-session identity before enablement, write the initial durable state before publishing enabled configuration, reject overlapping same-kind targets and join the live scheduler. The WPF Add dialog browses for an executable or selects the known ChatGPT package, displays the discovery result and explains the wait-for-first-start default. The Add dialog now accepts one literal launch argument per line and an optional full working-directory path for executables; the host validates the directory and stores these values for `ProcessStartInfo.ArgumentList`. A general installed-app picker remains pending. A failed configuration commit may leave an unreferenced ledger; it cannot become an enabled profile or be silently reused.
- The coordinator exposes durable pause/resume, enable/disable and Reset recovery commands. Pause/resume and enable/disable preserve the attempt count and lockout; reset rejects an in-flight launch, checks target presence, clears the episode budget durably and begins a fresh observation or absence/retry sequence. A failed state write degrades storage and prevents dispatch. The host runs per-profile commands independently off the WPF dispatcher, and dashboard rows expose these controls when applicable. Launch-identity editing and complete UI acceptance remain pending.
- Start now flows through the same coordinator and shared launch gate. It checks current-session identity immediately before dispatch, adopts a present instance, durably records an explicit pending operation before launching an absent target and does not charge or clear the automatic budget. A failed pending-operation write prevents dispatch. If launch reporting is uncertain, the coordinator waits through the appearance timeout instead of allowing an immediate duplicate. An interrupted explicit operation restores into a distinct hold, even when the automatic budget is zero; discovery and qualifying stable observation can rearm it under policy, or the user can explicitly reset recovery. The state file adds optional fields so existing schema-1 checksums remain valid. This conservative interrupted-explicit hold is a provisional M2 safety choice pending fuller restart/session validation. The dashboard exposes Start now for applicable executable profiles. A dispatch that reports failure after the adapter was entered is currently treated as uncertain for the full appearance timeout, even if the error may have been definite.
- Stop and pause commits a paused recovery state before asking the selected executable to close. Its Windows adapter rediscovers the current user's current-session match and rechecks PID, start time and canonical path on the process handle before graceful or forced close. A blocked graceful close returns a distinct force-choice result; the coordinator accepts a force call only for that pending operation/identity, while the dashboard asks the user separately. Unknown, ambiguous or changed identity never authorizes termination. The automatic attempt count stays unchanged and cancellation or a rejected force choice leaves protection paused. Restart now shares this verified close path, requires fresh absence, then performs a manual launch while retaining the profile gate through reservation and dispatch. Its separate in-memory completion token is single-use; a matching instance appearing before launch is adopted. Restart preserves the episode's automatic attempt count and lockout. This is wired through the host and WPF row, but the UI dialogs have not yet been inspected interactively; packaged-app stopping remains open. AT-13 is only partially covered.
- Disable and remove now cancel pending dispatch before committing configuration and detaching the scheduler; neither terminates the target. Re-enable opens the existing state file and fails closed if it is missing or damaged. Removed profiles leave their state file and events intact, while the dashboard no longer lists them. A stale configuration save rolls back the enablement ledger when possible. A disposable Windows target remained running through disable, re-enable and remove in the controlled integration test. Per-profile View history selects its current profile ID; removed profiles with retained events remain selectable in History.
- The WPF Edit policy dialog now changes the immutable profile's display name, monitoring/recovery policy and recovery/lockout notification preferences while showing target identity read-only. The host commits validated, revision-checked configuration under the profile coordinator's serialization gate for policy edits, so a stale save leaves the live policy unchanged. Observation-duration changes restart the current stability timer; retry-delay changes recompute the pending deadline from Save; the scheduler immediately reconciles with new intervals. An outstanding launch retains its original appearance deadline, attempt limit and retry delay until its result. Renaming keeps the same profile ID, ledger and history. Launch identity and richer setup remain open.
- The dashboard can duplicate a profile as a disabled copy. The copy retains target and policy settings but gets a new immutable ID, fresh zero-attempt state and no scheduler entry; the source ledger and target are untouched. The host writes the copy's state before publishing its configuration, leaving an orphan state file on a failed save rather than an enabled profile without trusted state. The button and confirmation text still need interactive layout/accessibility verification.
- The test suite covers deterministic recovery boundaries, restart reconstruction, damaged state and real Windows process behaviors. The Windows build workflow runs deterministic tests; process/window tests run in an interactive local session.
