# Application and scan diagnostics

Application diagnostics are enabled by default from primary-process startup. Open **Storage → Open diagnostic logs**, or **Settings → Local data → Open diagnostic logs**. Normal logs are under `%LOCALAPPDATA%\Relight\Logs\Diagnostics`; isolated previews use their own data directory. `application-*.jsonl` holds progress/resources/lifecycle; `scan-failures-*.jsonl` holds actual scan failures. Failure files are created only when failures occur. Restart the preview after rebuilding to activate new instrumentation.

After a recurrence, retain that folder promptly or use **Export diagnostic bundle** after restarting. The local ZIP includes separate `application-diagnostics.jsonl` and `scan-failures.jsonl` excerpts (each latest 500 valid records, at most 2 MiB) alongside the existing recovery events and redacted settings. Nothing is uploaded. Keep the original JSONL files when investigating a long scan because the export is a bounded recent excerpt.

## Completed scans with partial coverage

`ScanFinished` with stage `Completed` means the operation finished; its coverage can still be incomplete. Check the saved result's `TraversalComplete`, `EntryLimitReached` and `SkippedEntries` together. A finished traversal below its budget with skipped entries legitimately displays **PARTIAL SCAN — COVERAGE INCOMPLETE**. Protected/changed paths and intentional reparse/offline/recall exclusions remain gaps. New results have exact `IssueCounts` and separate Excluded, Failed and depth-limited totals; these count issue occurrences, including folders/enumeration, not distinct failed files. Up to ten local samples per category retain the first five and latest five (currently at most 100 overall). Older results only retained the first 100 issues: their split remains unknown until an explicit rescan.

The [1 November long-path investigation and correction](storage-checkpoint.md#long-path-coverage-correction--1-november-2026) confirmed that existing paths beyond the legacy Windows length limit could incorrectly report path-not-found. The corrected adapter uses normalized extended paths for native opens. Restart with the rebuilt application and explicitly rescan to replace older results; changing the entry budget cannot repair that historical coverage.

## Failure-only scan logs

**2 November 2026:** Start with `scan-failures-*.jsonl` when investigating skipped reads. Intentional exclusions do not produce failure events. Actual failures include access denied, missing/changed paths, sharing violations, unavailable metadata, interrupted enumeration, other native I/O failures and size-total overflow. Depth limits remain a separate coverage condition. Space usage shows separate totals, exact reason counts and a failure-only table; expected exclusions are collapsed below it. Raw sample paths remain only in the local scan baseline/UI, outside the diagnostic streams and bundle.

`ScanReadIssue` records the first exception detail for each admitted group. `ScanFailureSummary` records all cumulative failure counts and each group's first/latest timestamp, redacted path tag and allowlisted suffix. Group keys preserve category, operation, native Windows code and HRESULT. **Counts are cumulative: use the latest summary for each ScanId, rather than summing summaries.** Every failure updates the counters even when no detail is emitted. The shared worker flushes changed groups during its samples; new groups request a sample. Stage changes, cancellation/completion and orderly diagnostics shutdown also flush pending groups. The latest native code is retained on heartbeat/phase snapshots, rather than only a generic Win32Exception HRESULT.

There are at most 24 detailed code/operation groups plus one overflow group per failure category (currently eight). `GroupingLimited` and `OtherCodes` explicitly identify coalescing: total/category counts remain exact, but overflow groups do not claim a complete per-code breakdown. First/latest examples keep later failures visible without per-file disk writes. Scan/persistence exceptions also appear as `ScanFailed` in both streams; a persistence error does not increment file-failure counts or inherit the last file's path/operation. Canceled scans keep diagnostic evidence while retaining the prior saved baseline.

The existing background worker and bounded queue serve both streams. Each failure segment is at most 2 MiB, with at most four per process lifetime and a seven-day/8 MiB soft failure-stream retention target; the application stream retains its separate seven-day/32 MiB target. Retention only touches exact owned filenames in the corresponding stream and skips reparse files. Active/blocked files may prevent retention. Queue loss, capture/write failure and blocked retention use the existing visible degraded status; full scan counters in a saved result remain independent of log delivery. Forced termination cannot flush pending in-memory changes, and rotation/export bounds can remove older details, so neither log promises every individual path or unlimited history.

Reproduce the isolated native workflow with `pwsh -File scripts/Test-StorageUi.ps1 -ExerciseScanFailures -ExerciseScanLimit -ExerciseCleanup`. The harness uses a disposable junction and an exclusively held empty directory, verifies Excluded: 1 / Failed: 1 plus native sharing code 32, then removes those fixtures and rescans to complete coverage. It does not change the user's scan or delete real files.

## Protected-system access failures

New scans classify access-denied/sharing errors (Windows codes 5, 32 or 33) in a small allowlist as `ProtectedSystemAccess`. They remain in **Failed**, with **Protected system**, **Access restricted** and **Other errors** subtotals. Access restrictions have a folder table and separate collapsed samples; the main error table contains remaining read errors. Protected samples have their own collapsed section. All remain in `scan-failures` logs with their original native code, operation and redacted samples. Diagnostic scan snapshots expose `ProtectedSystemFailed`, `AccessRestricted` and `OtherErrors` alongside total `Failed`; the older `OtherFailed` field continues to mean every non-protected failure, including access restrictions. Partial warnings remain attached even if every failure is protected or access-restricted.

The allowlist uses the actual common-data and Windows paths: `Microsoft\Crypto\Keys`, `Microsoft\Crypto\SystemKeys`, `Microsoft\Crypto\RSA\MachineKeys`, `Microsoft\Crypto\DSS\MachineKeys` under common data; `System32\config` under Windows; `$Recycle.Bin` and `System Volume Information` on the Windows drive; the Windows `Temp` root exactly; and exact Windows-drive root files `DumpStack.log`, `DumpStack.log.tmp`, `hiberfil.sys`, `pagefile.sys`, `swapfile.sys`. It does not match similarly named sibling directories, arbitrary user folders, the entire Windows tree or every Temp descendant. Missing/changed paths and other errors remain ordinary failures inside these locations. A protected label describes location, not an ACL audit or proof that a denial is benign.

This classification performs no filesystem reads of its own and changes neither native read attempts nor permissions, scan scope, measured sizes or cleanup. New baselines store `FailureClassificationVersion: 1`; earlier S12 results keep their original Failed/Excluded counts but show an unknown protected/other split until explicitly rescanned. Saved evidence is not rewritten on loading. Unsupported classification versions are rejected with the original baseline preserved.

**Access restricted describes unavailable access, not an ACL audit.** The protected-system allowlist remains deliberately narrow. The [4 November investigation](storage-checkpoint.md#remaining-access-denials--4-november-2026) found that all 935 remaining failures were access denials, including system, managed-application, other-user and temporary lock locations. These now appear as Access restricted rather than being mixed with other error types. The adapter already opens metadata with zero content access; [Windows still applies security restrictions to such opens](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew). Relabeling a denial does not recover the missing size or establish complete coverage.

## Access-restricted folder counts

New scans save `AccessRestrictions` version 1 alongside the existing category counts. The folder table counts all `AccessDenied` occurrences independently of the first/recent raw samples. It does not include protected-system failures, even those with native code 5. Metadata-read failures are assigned to their containing folder; directory-list/root-validation failures to that folder itself. Deeper locations roll up after five folder levels below the scan root. Every restriction is assigned once: parent rows are not subtotals of separately listed children.

At most 128 normalized case-insensitive folder names of at most 1,024 characters are retained. New names beyond those bounds or unsupported paths increment a visible **Other folders (not individually retained)** row; admitted folders keep exact assigned counts. Rows sort by descending count. All rows, including the remainder, sum to Access restricted. The count does not estimate files hidden inside an unreadable folder. Raw folder names stay in the local baseline/UI, outside diagnostic logs and exports; scalar AccessRestricted/OtherErrors counters accompany existing redacted failure groups.

An older categorized scan can immediately show its exact Access restricted total. Its folder table explicitly counts **Retained samples**, with unknown full folder counts and a rescan instruction. It never treats ten sample paths as a complete inventory of hundreds of failures. Earlier uncategorized scans keep unknown totals. Loading performs no rewrite, and validation rejects unsupported grouping versions, inconsistent totals, duplicates, paths outside the root and invalid bounds while preserving evidence. Existing scan budgets, 100-sample/4 MiB baseline limits and cleanup behavior remain intact.

`pwsh -File scripts/Test-StorageUi.ps1 -ExerciseAccessRestrictions` loads a synthetic saved result with 935 restrictions assigned 900/30 plus a remainder of five, one protected-system failure and two other errors. It checks native displayed counts, separate samples/errors, retained partial coverage and unchanged saved bytes/no new failure events on load. `-ExerciseProtectedFailures` and `-LegacyProtectedResult` exercise older scans with sample-only folder counts and known/unknown protected splits.

`pwsh -File scripts/Test-StorageUi.ps1 -ExerciseProtectedFailures` checks the native split, collapsed/expandable protected samples and retained partial warning using synthetic saved metadata. `-LegacyProtectedResult` verifies that an older categorized baseline retains both failures visibly with an unknown protected split. Neither fixture starts a scan or generates new failure events by loading saved data.

## Evidence

Each JSONL record has UTC time, a process-lifetime session GUID, PID, sequence and cumulative lost-record count. Startup identifies application version, build configuration, module MVID, runtime, OS, architecture, processor count and Windows session. Ten-second samples capture working set/peak, private and managed memory, GC heap/fragmentation/load/pause/allocation/collection counts, cumulative CPU, handles, process threads and thread-pool availability/backlog.

Each scan has a GUID and entry budget. Stage records distinguish waiting for the worker, traversal, worker completion awaiting the UI, persistence, comparison and presentation. Samples include inspected/measured/skipped/alias counts, classified gap counts, identity-set size, traversal depth, elapsed/stage/progress age, cancellation, coverage and budget-stop state. The last metadata read or directory-enumeration operation records whether it is pending and for how long. Instrumentation brackets native reads and enumeration; no per-file disk log is written. The failure stream replaces the former first-five-only allowance with bounded group details and cumulative summaries throughout the run. Initial exception details include type, HRESULT/native code and up to 20 method/IL frames. Unhandled dispatcher/domain exceptions and unobserved task exceptions retain their redacted application-stream detail. Exceptions are not marked handled by logging.

A background-priority dispatcher probe has at most one outstanding callback. An outstanding probe delayed at least 20 seconds emits `DispatcherDelayed`; a later reply emits `DispatcherRecovered`. This is evidence of delayed dispatch, not proof of a hang: debugger suspension, machine sleep or severe resource starvation can delay replies too. A scan `AwaitingUi` marker is emitted on the worker before returning to the dispatcher, helping separate completed traversal from delayed UI work.

Raw scanned paths, error messages, file contents, credentials, command arguments and environment contents are excluded. Paths become 16-hex SHA-256 correlation tags plus drive letter and a small allowlist of file suffixes. Tags permit comparison within evidence; they are not reversible path lookup. This also means logs alone may identify a slow category/operation without identifying a particular private filename. Method names and IL offsets need the matching build/MVID for deeper analysis. These are telemetry records, not heap dumps or live hung-thread stack captures.

## Bounds and failures

One process-wide background diagnostics thread performs sampling and file writes independently of the WPF dispatcher and shared thread pool. This deliberate exception to ordinary shared-scheduler work prevents UI/thread-pool starvation from stopping diagnostics; it is not a thread per monitored profile. Producers only update bounded state or enqueue records and never wait for log I/O. The queue holds 256 records, each capped at 32 KiB. Sampling also occurs on phase changes.

Owned `application-<session GUID>-<segment>.jsonl` files rotate at 2 MiB, retaining at most four segments per process lifetime, with a seven-day/32 MiB soft aggregate retention target. Cleanup only touches exact owned filenames, skipping reparse files. Active locked files or filesystem failures may prevent retention and exceed the aggregate target; exported bundles are unaffected. Each appended line is flushed through to disk. A partial failed write moves to a new segment; export skips malformed tails. No configuration, scan baseline, cleanup history or arbitrary user file is deleted by this retention.

Queue loss, write/capture failures and blocked retention appear in Settings status and a global degraded banner while the UI is responsive. Lost-record counts remain visible after writes recover. Writes retry on later records; a full/unavailable disk still limits evidence. Normal shutdown drains with a two-second bound and writes `ProcessStopped`; fatal exception hooks request a best-effort 250 ms flush. Forced kill cannot run shutdown hooks. Previously flushed records survive, but the newest samples may be absent. A missing stop marker means an incomplete session, not a proven crash or a root cause.

## Verification and limits — 29 October 2026

Six deterministic tests cover dispatcher delay/recovery with one pending probe, correlated scan counters, bounded issue sampling, queue overflow, write-failure recovery, owned-file rotation/age retention, malformed-tail handling, export bounds and message/path redaction. A disposable process probe creates its own blocked STA dispatcher and pending metadata marker, waits for flushed live evidence, terminates only its child and verifies retained redacted records without a stop marker. It does not run a real C-drive scan or block real filesystem I/O.

Run the probe after a Release build:

```powershell
tools/Relight.DiagnosticsProbe/bin/Release/net10.0-windows/Relight.DiagnosticsProbe.exe artifacts/diagnostics/new-isolated-run
```

Use a fresh evidence directory. The report and JSONL are ignored local artifacts. Full-drive endurance, original freeze reproduction/root cause, debugger-hang stack capture, sleep behavior and log-write latency on a failing disk remain unverified. This increment adds evidence and does not claim to fix the reported twenty-minute freeze. Real cleanup consent and settings are unchanged.
