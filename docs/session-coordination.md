# Session and recovery-budget coordination design

**Status:** M0/M2 design with shared-budget/session-state repositories, fail-closed legacy migration and internal host/coordinator integration tests; production rollout and multi-session validation remain open.  
**Requirements:** [PRD Section 10](PRD.md#10-persistence-and-data-model), [AGENTS.md](../AGENTS.md), [development plan M2](development-plan.md#m2--make-configuration-and-recovery-state-durable).

Relight currently stores one revision-checked recovery snapshot per profile under `State`. A file lock serializes each read/replace, and a stale revision stops a second writer. This prevents two simultaneous commits from both succeeding, but it does not give each signed-in Windows session its own observation state. A second session can restore a snapshot based on another session's process, then fail later with a stale revision. The current implementation is therefore a safety foundation, not fulfillment of the multi-session requirement.

`SharedRecoveryBudgetStore` provides a versioned, checksummed `Budgets/<profile>.json` repository with a per-profile cross-process lock, durable replacement, explicit and automatic pending-operation markers, exact-cap reservation, revision checks, lockout, stable-observation release and explicit reset operations. It records episode creation before an attempt, and neither stable observation nor Reset can erase an unresolved launch marker. `RecoverySessionStateStore` stores a checksummed live checkpoint under `Sessions/<opaque-logon-key>/State/<profile>.json`, refuses missing or stale shared budgets, and initializes a new sign-in without claiming another session's pending operation. A durable `State/<profile>.session` marker in that session directory distinguishes a genuinely new sign-in from a lost checkpoint in a known sign-in. Its shared-budget revision is optional in the legacy checkpoint format so old checksums remain valid. An opt-in `ProfileCoordinator` path commits episode creation, reservations, launch resolution, lockout and budget release to these stores before writing session state. It performs one more discovery after a charged reservation or explicit-start marker and records `LaunchAverted` or `ExplicitStartAverted` instead of dispatching if a target appears or inspection becomes unavailable. On a same-session restart, a matching pending marker is reconciled after verified target presence or a full fresh appearance timeout of reliably repeated absence. The shared scheduler polls at the observation interval during this wait; an unavailable lookup, pause, disable or missed poll restarts it. The attempt stays charged. Pause and disable preserve marker ownership in the session checkpoint, while a marker owned by another session suspends automatic actions and is never resolved locally. Focused tests cover these boundaries, exact-cap failures, stable release, distinct explicit-start accounting and stale cross-session revision rejection.

An internal `RecoveryApplicationHost.OpenSharedSessionAsync` path now composes the repositories with the current token's opaque logon key. It distinguishes fresh profiles, existing session files, a genuinely new sign-in, guarded legacy migration, missing state and partial migration. Controlled host tests cover fresh registration/reopen, disabled duplication and later enablement, legacy migration preserving the old bytes, and missing budget or missing same-session checkpoint suspending automatic actions. An explicit internal repair path can finish an interrupted migration only when a trusted shared budget exactly matches the imported legacy snapshot and any existing session checkpoint matches the expected initial state. A missing or changed budget, or conflicting session checkpoint, remains suspended without overwriting evidence. The migration and repair switch is internal to tests; normal `OpenAsync` and the WPF application still use legacy state. The tested host path is not a production rollout: cross-process validation of older-binary isolation, repair for other partial transfers and real two-session evidence remain open. M2 is not complete.

The internal shared host now wraps active-profile discovery with a shared-configuration revision/hash check before and after each lookup. If another sign-in changes, removes or corrupts the configuration, that host reports detection unavailable and cannot use its cached profile to launch or stop a target. A controlled host test covers an external profile removal and rejection of explicit Start now without changing the budget. The guard suspends stale actions until reconciliation; a cross-process edit remains possible in the tiny interval after the final check. Normal WPF startup does not use this guard.

An internal `ReconcileSharedConfigurationAsync` operation reloads a valid changed configuration, waits for outstanding commands, removes stale scheduled profiles without stopping their targets, and rebuilds profiles using the new settings and trusted session/budget state. Controlled tests cover a remote name/policy edit, removal with the budget preserved, addition with a trusted budget, and addition with no budget remaining passive. The internal shared host's resident run loop now checks every two seconds and invokes reconciliation when configuration changes. A failed reload sets a visible configuration problem and suspends the host; a later valid repair retries and rebuilds. Controlled run-loop tests cover a remote edit and invalid configuration followed by last-good repair. Production WPF integration remains open. A configuration change during rebuilding is caught by the discovery guard and suspends actions until another reconciliation. There is no atomic cross-process configuration/launch transaction yet.

`WindowsLogonSessionIdentity.Current()` now reads the current token's `TOKEN_STATISTICS.AuthenticationId`, user SID and Windows session ID, deriving an opaque storage key without embedding the SID in a file name. A local Windows test returned the same identity on repeated calls, and a disposable console probe returned the same key from two separate processes in this sign-in. A second sign-in and reboot have **not** been tested; the internal shared-session host derives and uses this key, while the normal WPF host remains on legacy state. The probe's source/output lives only under ignored `artifacts/session-probe`.

## Ownership and records

- Identify a live session by the current user's SID plus a logon-session identifier and Windows session ID. Microsoft documents the logon SID as `S-1-5-5-X-Y` and `TOKEN_STATISTICS.AuthenticationId` as a LUID for the logon session ([well-known SIDs](https://learn.microsoft.com/en-us/windows/win32/secauthz/well-known-sids), [token statistics](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-token_statistics)). `whoami /groups` in this development process did not expose a logon SID, so the token authentication LUID is the implemented identity source. Same-sign-in process stability is verified; separation across sign-ins and reuse across reboot remain to be tested before this key controls session files. Never use the numeric session ID alone.
- Retain one revision-checked shared configuration. Every edit uses the revision and content hash; a stale edit reloads and asks the user to apply it again. The active hosts must reconcile added, removed, enabled and edited profiles after another session commits a new revision. A host that cannot reconcile must suspend affected automatic actions.
- Introduce one **shared per-profile budget ledger** as the authority for episode ID, reserved automatic attempts, limit-independent lockout, manual reset, pending dispatch and revision. Only this ledger can authorize an automatic dispatch. It must be valid before a session starts recovery; missing/corrupt shared state for an existing profile suspends launches.
- Introduce **per-logon-session live state** for target instance, observation provenance, pause/armed state, monitoring gaps and monotonic deadlines. It never authorizes an attempt from its own counter. A new sign-in begins with fresh discovery and observation while importing the shared budget/lockout. A Relight restart in the same sign-in restores conservatively and starts new monotonic deadlines.
- Keep process identity tagged with its source logon session. An instance from another session is never adopted, closed or used to earn stability in this one. Persisted PID/start time is diagnostic only, never authority for termination.

## Automatic dispatch transaction

1. Serialize this profile in the local coordinator, acquire the global launch gate, and discover the current session again. Unknown or ambiguous detection stops here.
2. Under an exclusive per-profile cross-session ledger lock, reload and validate the shared ledger. Check lockout and the exact cap against its current revision. A stale local view must rebase or suspend; it cannot dispatch using its earlier count.
3. Reserve the next attempt and operation ID in the shared ledger with a durable flush and atomic replacement. Do not dispatch if that commit fails. A crash after this point consumes the attempt, even if no launch call was made. An unresolved marker also prevents Reset from clearing that reservation.
4. Recheck current-session absence immediately before dispatch. If the target appeared after reservation, adopt it and retain the charged attempt; record that the dispatch was averted. If detection became unknown, retain the charge and suspend. This ordering favors a possible charged non-dispatch over an unaccounted launch.
5. Dispatch once, then write session observation status. A dispatch error still consumes the reservation; an uncertain result holds the outstanding operation until a full appearance timeout and reconciliation. A later host never refunds a pending reservation merely because its session checkpoint is absent.

Explicit Start now uses its own durable pending-operation marker and the same fresh-discovery/global launch gate, but does not increment the automatic count. Reset recovery is an explicit ledger transaction. Stable observation may clear the shared budget only after qualifying uninterrupted verification in the current session and under the same ledger lock. A session that was already healthy before another session's lockout must not clear that lockout from stale local observation; it must begin a new qualification against the current episode/revision. Increasing the configured limit alone never clears lockout.

## Migration and failure handling

The existing `State/<profile>.json` is a schema-1 mixed snapshot. `RecoveryStateStore.MigrateToSession` takes that profile's legacy lock, validates its checksum/revision, then durably writes an ownership marker in `State/<profile>.owner`. While holding that lock, it atomically moves the original bytes to `State/<profile>.legacy.json` and writes a durable, intentionally invalid tombstone at the old path **before** creating the shared ledger and fresh session checkpoint. Older published readers require the old path to load or save attempts, and older creators see an existing file; their next state operation fails closed. An already-reserved launch may still finish and is imported as a pending shared operation. The marker changes from `migration-pending` to `session-owner` only after both new records are durable. Upgraded legacy `Create`, `Load` and `Save` reject either marker; the archived original and its existing backup are preserved. If transfer stops after archival, explicit repair verifies the archive, tombstone, existing revision-one shared budget and initial session checkpoint before completing ownership. It can recreate a missing tombstone from the archive but does not recreate a missing budget, recover a changed budget, or overwrite a conflicting checkpoint. A session marker without a checkpoint stays suspended. Damaged legacy state stops before marker creation. The internal host can invoke migration/repair only with an explicit test switch; normal WPF startup does not invoke it.

Cross-file updates cannot be one atomic filesystem replacement. The shared ledger is written first at every budget or dispatch boundary; a session file may lag and must be reconstructed from the ledger. The archive/tombstone gate makes known older versions' next state read or write fail, including a version that cached the old checkpoint before migration. `pwsh -File scripts/Test-LegacyMigration.ps1` builds the pre-marker storage and coordinator implementation from commit `bbd5879` in separate processes. On this Windows 11 x64 desktop, a cached old-storage Save failed with `RecoveryStateUnavailableException`, Create failed with `InvalidOperationException`, the archived SHA-256 matched the original, and the tombstone remained. In a second case, an old coordinator reserved an automatic attempt before migration, waited in a fake launcher, then completed exactly that one dispatch afterward. The new shared ledger retained one pending attempt; a new coordinator marked its unmatched operation degraded and did not dispatch another launch. The script runs in Windows CI. These probes use fake adapters and a temporary profile, not a whole older WPF app or a real installed target. Versions with different state access behavior, a failed archive/tombstone transaction, and two real sign-ins still require rollout validation before the shared path is enabled. General repair for uncertain/missing budget evidence is not implemented.

## Evidence required before enabling multi-session recovery

- Two real concurrently signed-in interactive sessions on Windows, with one target instance in each. Show each host sees only its own target and never terminates the other's process.
- Competing automatic launch attempts at the final available count. Exactly one reservation succeeds; neither session can dispatch beyond the shared cap. Inject crashes before reservation, after reservation and before dispatch.
- Lockout in session A, sign-in to B, pause/resume and policy-limit edits in both, then Relight restart. The lockout persists until explicit reset or a newly qualified stable observation under the rearm rule.
- Configuration edits in both sessions. Demonstrate stale revision rejection and live reconciliation or a visible suspended state.
- Session ID reuse, logoff, sleep/unlock, clock changes and unavailable/corrupt ledger files. No gap or wall-clock change grants observation time or extra attempts.

Until that evidence exists, M2, AT-11/AT-14/AT-15 and M8 cross-session acceptance remain open. This design does not claim that the present shared snapshot implementation meets them.
